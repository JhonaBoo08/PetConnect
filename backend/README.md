# PetConnect API

The backend is an Express/TypeScript API backed by MySQL 8. Firebase Authentication supplies user identity; the API verifies Firebase ID tokens and enforces PetConnect roles, ownership, privacy, clinic authorization, and recovery-token rules.

## Local setup

From the repository root:

```bash
npm ci
npm --prefix backend/api ci
npm --prefix frontend ci
```

Copy `backend/api/.env.example` to `backend/api/.env`, create the local database named in that file, then:

```bash
npm run db:bootstrap
npm run db:status
npm run emulators
```

In another terminal:

```bash
npm --prefix backend/api run dev
```

Local development may use MySQL root/blank password and the Firebase `demo-petconnect` emulator project only when that matches the developer's local MySQL configuration. Production explicitly rejects these development defaults.

## Configuration

Important API variables:

- `MYSQL_HOST`, `MYSQL_PORT`, `MYSQL_USER`, `MYSQL_PASSWORD`, `MYSQL_DATABASE`
- `FIREBASE_PROJECT_ID`
- `FIREBASE_AUTH_EMULATOR_HOST` for local emulator use only
- `GOOGLE_APPLICATION_CREDENTIALS` or `FIREBASE_SERVICE_ACCOUNT_JSON` in production
- `CORS_ALLOWED_ORIGINS`
- `PUBLIC_APP_BASE_URL`
- `RECOVERY_TOKEN_SECRET`
- `UPLOAD_DIR`
- optional `EXPO_ACCESS_TOKEN` when Expo push enhanced security is enabled

When `NODE_ENV=production`, startup requires explicit safe values, HTTPS public origins, a non-root database user/password, real Firebase Admin credentials, a stable non-placeholder recovery secret of at least 32 bytes, and an absolute durable upload path.

## Authentication and roles

Owner self-registration uses Firebase email/password and `POST /v1/account/initialize`. Clinic accounts are operator-provisioned; ordinary account creation does not grant clinic role.

Protected requests use `Authorization: Bearer <Firebase ID token>`. Token verification checks revoked/disabled sessions. Owner and clinic routes enforce role and relationship checks server-side.

## Pet CRUD and photos

Owner-scoped routes:

- `GET /v1/pets`
- `POST /v1/pets`
- `GET /v1/pets/:id`
- `PATCH /v1/pets/:id`
- `DELETE /v1/pets/:id`
- `PUT /v1/pets/:id/photo`
- `DELETE /v1/pets/:id/photo`

Pet IDs are generated by the API. Cross-owner access does not reveal another owner's pet.

Pet photos accept valid JPEG/PNG/WebP input within configured limits. The server decodes the image with Sharp, rejects unsafe dimensions/pixel counts and malformed content, rotates/resizes it, re-encodes to WebP, removes original metadata, and uses a generated filename. Replaced/removed/deleted pet photos are cleaned up when the file belongs to local managed storage.

## Pet ID and public recovery

Owner routes:

- `GET /v1/pets/:id/recovery`
- `POST /v1/pets/:id/recovery/rotate`
- `DELETE /v1/pets/:id/recovery`

Public recovery uses a signed high-entropy token. The QR URL has the form:

```text
https://your-app.example/recover?token=<token-id>.<signature>
```

Rotation invalidates the previous token and revocation disables the current token. Public output intentionally excludes Firebase UID, private database identifiers, health records, clinic records, appointments, authentication claims, hidden contact details, and hidden recovery-location precision.

## Recovery network and notifications

Owner recovery routes create/read/reunite lost reports. Public finder routes accept sightings and the nearby feed returns recovery-safe information. Location is foreground-only; PetConnect does not implement continuous background tracking.

In-app notifications are durable MySQL rows. Native Expo push is optional. Successful Expo push tickets are recorded for receipt checks; `DeviceNotRegistered` disables the affected token so later notifications do not repeatedly target it.

## Health and clinic workflows

Authenticated owner APIs cover health records, vaccinations, reminders, clinics, and appointments. Reminder and appointment notification jobs use the MySQL `scheduled_notifications` queue.

Clinic patient lookup uses a valid PetConnect recovery token plus an authenticated active clinic account. The QR identifies the pet; it does not by itself grant unrestricted clinical access. Clinical history/write access follows the appointment/relationship rules in `health-clinic.ts`.

## Database migrations

`sql/schema.sql` is the canonical complete schema for fresh databases. `sql/migrations/` contains ordered changes for existing databases. The maintenance tool records SHA-256 checksums and refuses migration-history drift.

```bash
npm run db:bootstrap
npm run db:status
npm run db:migrate
```

Do not edit a migration that may already be applied in a shared environment.

## Backup and restore

```bash
npm run db:backup -- --output <backup-directory>
npm run db:restore -- <backup-directory>
```

A backup set includes the database dump, upload archive, and metadata. Restore testing must use a disposable database and a separate `UPLOAD_DIR`, never live data. Copy production backups off the application VM.

## Health and logs

- `GET /v1/health` confirms the process is serving HTTP.
- `GET /v1/ready` verifies database readiness.
- Request logging includes request IDs.
- Error responses/logs must not expose secrets.

On a simple VM deployment, monitor the service log, `/v1/ready`, disk usage for MySQL/uploads, and backup job results. A large observability stack is not required.

## Tests

```bash
npm run check:backend
npm run test:backend
```

`npm run test:backend` starts the Firebase Auth emulator around the integration suite and requires a disposable MySQL database called `petconnect_test`. Never aim this command at production.
